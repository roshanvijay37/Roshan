02Before the day

Send this to every student 3 days ahead and ask for a screenshot of claude --version working. Without it, 20 minutes of the session goes on installs and Wi-Fi.

  • Claude Pro subscription active ($20/month; Claude Code is included)
  • VS Code installed, with the Claude Code extension
  • Git installed (on Windows, Git for Windows also gives Claude Code a Bash shell)
  • Node.js LTS installed (node -v works)
  • Claude Code installed. Windows PowerShell: irm https://claude.ai/install.ps1 | iex. Mac or Linux: curl -fsSL https://claude.ai/install.sh | bash. Then open a new terminal and run claude --version
  • Ran claude once and logged in with the Pro account
  • Free accounts created: GitHub, Vercel (sign in with GitHub), Supabase
  • token.txt created outside the project, with VERCEL_TOKEN and GITHUB_TOKEN filled in (steps in Tokens). The Supabase values are added on the day
  • Phone charged, to test their own app on a real device
On the day: have a spare hotspot. Pair anyone whose setup failed with someone whose setup worked. They still learn by driving.

03How I work with Claude

Treat Claude as a capable engineer you hand a whole job to. Don't treat it as an autocomplete you feed one line at a time.

  1. Hand over the outcome, not the steps. A good brief has a goal, the rules, the phases, and what "done" means. It ends with "don't stop between phases to ask me". A vague ask gets a vague result.
  2. Plan first for anything bigger than one page. Press Shift+Tab into plan mode, read the plan, correct it, and only then let it build. Fixing a plan costs one message. Fixing finished code costs twenty.
  3. Let it operate the tools, not only write code. Claude can run git, push to GitHub, deploy, read build logs and fix the error itself. When a task ends with "and then upload it", ask Claude to do the upload too.
  4. Make it prove things work. Ask it to run the app, open it and check the page. Then ask: "What did you actually test, and what didn't you?" Claude can't touch your phone, so you test on the device yourself.
  5. Keep what works. In a redesign, say "keep every existing feature, restyle only". Prefer adding over rewriting, so nothing that works quietly disappears.
  6. Write the lesson down. When something costs you an hour, put the fix in CLAUDE.md so the next session knows it. Example: my Vercel deploys were silently blocked until commits used the Vercel account's email. That lesson is one line in my CLAUDE.md now.
Example brief 
Build a booking website for my friend's salon in Moodbidri.
Rules: mobile first, fast, no login for customers, Kannada + English.
Phases: 1) plan the pages and show me, 2) build, 3) run it and check every
page on a phone-sized screen, 4) push to GitHub and deploy to Vercel.
Done = a live URL that works on a phone. Don't stop between phases 2-4.

05Build 1 · A live website in 45 minutes

The site goes live at a public URL and is about something real to the student: their portfolio, a family shop, a college club. A real subject gives a real brief, and a real brief gives a better site.

  1. 0–5 min · Set up. Make a new folder, open it in VS Code, and start Claude Code.
  2. 5–15 min · Brief and plan. Write the brief using prompt card 1. Press Shift+Tab for plan mode, read the plan, and fix one thing in it on purpose.
  3. 15–30 min · Build. Paste a screenshot of a site you like and say "match this feel, not this content". Plain HTML + Tailwind is fastest here; you don't need a framework.
  4. 30–38 min · Check. Open it in the browser's phone view (F12, device toolbar). Send each problem back to Claude as one sentence: "the menu overlaps the logo at phone width".
  5. 38–45 min · Ship. Ask Claude to commit with git and deploy with the Vercel CLI, using VERCEL_TOKEN from token.txt (see Tokens). Then open the URL on your own phone.
Teaching point: the students type almost no code. They write the brief, judge the result and report problems precisely. That is the job now.

06Build 2 · A real app with login and a database

The stack is the one real production apps use: Next.js + Supabase + Vercel, all on free tiers. Keep the app to one table plus login: an expense tracker, a club attendance list, shop orders or a reading log.

  1. 0–10 min · Brief. "Users sign up with email, add / edit / delete their own X, and see only their own."
  2. 10–20 min · Plan. In plan mode, ask Claude for the table design and its security rules (Supabase Row Level Security). Read both.
  3. 20–25 min · Create the Supabase project by hand (region: Mumbai). Put its URL, publishable key and project ref into token.txt (see Tokens). Claude writes .env.local from that file. Never paste the values into the chat.
  4. 25–55 min · Build. Claude writes the pages and a SQL file, and you run that SQL in Supabase's SQL editor.
  5. 55–65 min · Break it on purpose. Sign up as two users. User A must not see User B's rows; if they can, the security rules are wrong. These are the most important 10 minutes of the day.
  6. 65–75 min · Ship. Claude deploys to Vercel and adds the same two environment variables there. Then open the app on your phone.
Rule 1: only the publishable key (sb_publishable_…, the old "anon" key) goes in the app. The secret key (sb_secret_…, the old "service_role" key) never goes in frontend code, because it bypasses every security rule.
Rule 2: Supabase's free tier allows 2 active projects per account. Pause old ones before starting new ones.

06bTokens · one file, read safely

A token lets Claude act on a service for you: deploy, create a repo, run SQL. Keep all of them in one file outside your project, token.txt. Tell Claude where it is, and Claude reads one value at the moment it needs it, without ever printing it.

What you buildTokens you need
Simple one-file demo appVERCEL_TOKEN
Build 1 · websiteVERCEL_TOKEN (+ GITHUB_TOKEN to keep the code on GitHub)
Build 2 · app with login + databaseVERCEL_TOKEN, GITHUB_TOKEN, SUPABASE_ACCESS_TOKEN, SUPABASE_PROJECT_REF, NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY

Step 1 · Create the file, outside the project folder. On Windows it goes at C:\Users\<you>\tokens\token.txt; on a Mac, ~/tokens/token.txt. Outside the project means it can never be committed by accident.

~/tokens/token.txt 
# My tokens. Never commit, never share, never paste into a chat.
# Created: [date]   Expires: [date]

VERCEL_TOKEN=
GITHUB_USER=
GITHUB_TOKEN=
SUPABASE_ACCESS_TOKEN=
SUPABASE_PROJECT_REF=
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=

Step 2 · Get each token and paste it after its =, with no quotes or spaces. Every one of these is shown only once, so copy it straight into the file.

  1. VERCEL_TOKEN. Open vercel.com → avatar → Account Settings → Tokens. Click Create, name it claude-session, set scope to your account and expiry to 7 days, and copy it. (Vercel docs)
  2. GITHUB_TOKEN. Open github.com → avatar → Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token (classic). Name it claude-session, set expiry to 7 days, tick only the repo scope, generate and copy it. Put your GitHub username in GITHUB_USER.
  3. SUPABASE_ACCESS_TOKEN. Open supabase.com/dashboard/account/tokens → Generate new token. Name it claude-session, set a short expiry and copy it. It lets Claude run your SQL for you, so there's no copy-paste into the SQL editor. (Supabase docs)
  4. SUPABASE_PROJECT_REF + URL. Open your project and click Connect at the top. Copy the Project URL (https://<ref>.supabase.co) into NEXT_PUBLIC_SUPABASE_URL. The <ref> part on its own goes into SUPABASE_PROJECT_REF.
  5. NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY. In the same Connect dialog (or Project Settings → API Keys), copy the publishable key, which starts sb_publishable_. Not the secret key. (Supabase docs)

Step 3 · Tell Claude the rules. Paste this into the project's CLAUDE.md. It's the same rule I use on all my projects.

CLAUDE.md · Tokens 
## Tokens
All tokens are in ~/tokens/token.txt as NAME=value lines.
- Read ONE value at the moment you need it, into a shell variable, e.g.
  VT=$(grep -m1 '^VERCEL_TOKEN=' ~/tokens/token.txt | cut -d= -f2- | tr -d '\r')
- NEVER cat/print/open the whole file. NEVER echo a value. NEVER copy a token
  into the project, a commit, a log or a reply. Write the NAME, never the value.
- .env.local may hold ONLY the NEXT_PUBLIC_* values. Check .gitignore has .env* first.
- Redact any URL echoed back by git: pipe through  sed -E 's#https://[^@]*@#https://#g'

Step 4 · How Claude uses them. You don't type these commands; Claude does. Show them so students recognise what they're approving.

Deploy to Vercel 
VERCEL_TOKEN=$(grep -m1 '^VERCEL_TOKEN=' ~/tokens/token.txt | cut -d= -f2- | tr -d '\r') \
  npx vercel --prod --yes
Create a GitHub repo and push 
GH=$(grep -m1 '^GITHUB_TOKEN=' ~/tokens/token.txt | cut -d= -f2- | tr -d '\r')
U=$(grep -m1 '^GITHUB_USER=' ~/tokens/token.txt | cut -d= -f2- | tr -d '\r')
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $GH" \
  https://api.github.com/user/repos -d '{"name":"my-app","private":true}'
git push "https://x-access-token:$GH@github.com/$U/my-app.git" HEAD:main 2>&1 \
  | sed -E 's#https://[^@]*@#https://#g'
Run SQL on Supabase 
ST=$(grep -m1 '^SUPABASE_ACCESS_TOKEN=' ~/tokens/token.txt | cut -d= -f2- | tr -d '\r')
REF=$(grep -m1 '^SUPABASE_PROJECT_REF=' ~/tokens/token.txt | cut -d= -f2- | tr -d '\r')
curl -s -X POST "https://api.supabase.com/v1/projects/$REF/database/query" \
  -H "Authorization: Bearer $ST" -H "Content-Type: application/json" \
  -d '{"query":"select now()"}'
Why "one value, never the file": anything Claude prints becomes part of the conversation and is saved in its history. A token read into a variable is used and never shown.
After the session: the tokens expire in 7 days. To be safe, delete them on each site's token page the same evening. If one ever lands in a chat or a commit, delete it and make a new one.

07Teach Claude your rules

Writing things down is the difference between using Claude and working with it. Claude forgets everything between sessions unless you write it down, and three places hold what it should remember.

Exercise (30 min). Each student writes two things:

  1. A 10-line CLAUDE.md for the app they just built: what it is, the stack, how to deploy it, and one rule ("never put the service-role key in frontend code").
  2. One skill, /ship, below. Then type /ship and watch it run. That is the moment it clicks.
.claude/skills/ship/SKILL.md 
---
name: ship
description: Check the app works, then commit and deploy it to Vercel. Use when I say "ship it".
---
1. Run the build. If it fails, fix it and run it again.
2. Open the main pages at phone width; fix anything broken.
3. Commit with a clear message, then deploy with `npx vercel --prod`.
4. Reply with the live URL and a list of what was and wasn't tested.

08Safety rules

Claude makes you fast, and fast mistakes are expensive. Each of these rules comes from a real incident.

  1. Secrets live in .env files, never in code, chat or Git. Check that .gitignore lists .env* before the first commit. If a key leaks, rotate it the same day.
  2. Names travel, values never. It's fine to write SUPABASE_URL in a doc or a prompt; the value itself never goes there.
  3. Back up before touching real data. Before any change to a live database: dump it, test, and keep the backup. Never let Claude experiment on real customers' data.
  4. Ask "what did you actually test?" "It builds and passes tests" is not the same as "it works on a phone". Know which one you have.
  5. Read before you approve. Claude asks before risky commands. Read the command first, especially anything that deletes, force-pushes or deploys to production.
